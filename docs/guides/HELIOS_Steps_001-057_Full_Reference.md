# Part 0 — The project

## 0.1 What HELIOS is

HELIOS is an **alpha-driven quantitative trading system**. It is a university project for the
CS24300 course at BIT Mesra, built by a team of three students, spanning three semesters
(5th, 6th, 7th).

It trades on **paper only**. No real money is used at any point. All market data is free and
public.

## 0.2 The priority order (fixed, and it matters)

1. **Alpha / quantitative research** — find trading signals that genuinely work after costs.
2. **Fault tolerance** — the system keeps working when parts of it fail.
3. **Low latency** — the system is fast.

This order decides what gets built first. A fast system with no working signal is worthless;
a working signal on a fragile system is still useful. Low latency is deliberately *last*.

## 0.3 The three semesters

| Semester | Focus | Main languages |
|---|---|---|
| **5th (now)** | Quantitative research platform: data, features, alphas, backtesting, paper trading, registry database | Python 3.12 |
| 6th | Machine learning (a graph + transformer model called DGT), manipulation detection (SpoofBench), the C++ hot path | Python, C++20 |
| 7th | Distributed matching engine, state-machine replication, chaos testing, formal specification, latency work | C++20, Go, TLA+ |

## 0.4 The horizon progression

The project deliberately starts slow and speeds up: **hourly → minute → second →
millisecond**. Reason: research mistakes are cheap to fix on hourly data and expensive on
millisecond data. Everything built so far works on hourly and minute data.

## 0.5 The integrity rules (these shape every technical decision)

1. **No invented results.** Every number must come from a run that recorded the code version,
   the settings and the data it used.
2. **No invented data.** Missing market data is reported, never filled in.
3. **No result typed by hand.** Documents that contain numbers are generated by scripts.
4. **Gates are criteria, not outcomes.** "Sharpe > 1" is what we *require* to accept an idea,
   never what we *claim* to have achieved.
5. **No claims the project cannot support.** No claims of co-location, FPGA hardware, or live
   trading, because none of those exist here.
6. **Decisions are written down before results exist**, with the date and the reasoning, in
   files called ADRs.

# Part 1 — Glossary

Read this once; every later part assumes it.

| Term | Meaning |
|---|---|
| **Alpha** | A trading signal: a rule that turns market data into a desired position (e.g. "hold +1 unit of BTC when the 24-hour return is positive"). |
| **Candle / kline / bar** | One time period of market activity summarised by five numbers: **open** (first traded price), **high**, **low**, **close** (last price), **volume** (amount traded). One hourly candle = one hour of trading. |
| **OHLCV** | Open, High, Low, Close, Volume — the five numbers above. |
| **Tick** | A single trade or quote event. Not used in the 5th semester; the data here is candles. |
| **Order book / L2 data** | The list of prices people are currently willing to buy and sell at. Used by the FI-2010 benchmark. |
| **bps (basis point)** | One hundredth of one percent. 10 bps = 0.10 %. Used for fees and slippage. |
| **Maker / taker fee** | A *maker* order waits in the book; a *taker* order trades immediately against what is there. Binance charges both 0.10 % at the basic level. |
| **Slippage** | The difference between the price you assumed and the price you actually get. |
| **Turnover** | How much of the position changes each period. 0.30 means 30 % of the position is traded each period on average. High turnover means high costs. |
| **Return** | Profit as a fraction of capital. 0.12 = 12 %. |
| **Sharpe ratio** | Average return divided by the variability (standard deviation) of return, annualised. It answers "how much profit per unit of risk?". A Sharpe of 1 is respectable; 2 is very good. |
| **Annualised** | Scaled to a one-year figure so that hourly and minute strategies can be compared fairly. |
| **Fitness** | A combined score used in alpha research: `Sharpe × sqrt(|annual_return| / max(turnover, 0.125))`. It rewards ideas that make money without trading excessively. |
| **Gate** | A pass/fail criterion an alpha must meet before it is accepted. HELIOS has six: G1–G6. |
| **Horizon** | How far ahead a prediction looks — 1 hour, 1 minute, 10 events, etc. |
| **Horizon family** | A group of horizons that share a "periods per year" number, so their Sharpe ratios are comparable. |
| **TRAIN / VALID / TEST** | Three time periods. TRAIN is used to build an idea, VALID to tune and compare, TEST to confirm once at the end. |
| **Embargo** | A deliberate gap between those periods, so a prediction made at the end of one period cannot be scored using data from the next. |
| **Leakage** | Accidentally using information that would not have been available at the time. It is the single most common way backtests lie. |
| **Out-of-sample** | Data the idea was not built on. |
| **Backtest** | Replaying history to see how a strategy would have performed. |
| **Paper trading** | Running a strategy live but with simulated money. |
| **UTC** | Coordinated Universal Time, the single time zone used everywhere in this project. |
| **Microsecond (µs)** | One millionth of a second. All timestamps in HELIOS are whole numbers of microseconds since 1 January 1970 UTC. |
| **Parquet** | A file format that stores data by column, compressed, with types preserved. Very fast to read. |
| **DuckDB** | A database engine that runs inside the program and queries Parquet files directly. No server needed. |
| **PostgreSQL** | A full database server. Used here for records about runs, not for market data. |
| **Migration** | A file that changes the database structure, kept in git and applied by everyone. |
| **Alembic** | The tool that runs those migrations. |
| **SHA-256 / checksum / fingerprint** | A 64-character code computed from a file's contents. If one byte changes, the code changes completely. Used to prove a download is intact. |
| **Lineage** | The record of which code version, settings and data produced a result. |
| **Seed** | A number that makes "random" operations repeat identically. |
| **Config hash** | A fingerprint of the settings used for a run. |
| **Linter** | A tool that reads code and reports mistakes and style problems (here: ruff). |
| **Type checker** | A tool that checks values match their declared kinds (here: mypy). |
| **Unit test** | A small check with a known right answer, run automatically. |
| **CI (continuous integration)** | Automatically running all checks on a clean machine whenever code is pushed. |
| **Macro-F1** | A score that averages performance over all classes equally, so a model cannot win by always predicting the most common class. |
| **Class imbalance** | When one answer is far more common than the others (here: "price stays flat"). |

## 2.1 Why WSL (Ubuntu inside Windows)

Every tool in the data and trading world is built for Linux first. WSL gives a real Ubuntu
inside Windows.

- **Alternative: plain Windows.** Rejected because Windows differs in file paths
  (`C:\x` vs `/home/x`), line endings (CRLF vs LF) and permissions. Code that works on one
  machine and fails on another wastes days, and the eventual deployment target is Linux.
- **Alternative: dual boot or a virtual machine.** Rejected as slower to work with day to
  day; WSL shares the same files and clipboard as Windows.

## 2.2 Why `uv` for Python

`uv` installs Python itself, installs libraries, and writes `uv.lock`, which pins the exact
version of every library and of every library's own dependencies.

- **Alternative: pip + requirements.txt.** Rejected: `requirements.txt` usually lists loose
  versions, so two people get different libraries and can get different numerical results.
- **Alternative: conda.** Rejected: heavier and slower to solve environments; on a slow
  internet connection this matters.
- **Practical benefit:** `uv sync --locked` on CI installs exactly what the laptops have.

## 2.3 Why Docker for the database

The database runs in a container, so every teammate gets **PostgreSQL 16** with the same
settings without installing anything.

- **Alternative: install PostgreSQL on Windows.** Rejected: versions drift between machines
  and uninstalling is messy.
- **Alternative: SQLite.** Rejected: the project needs proper constraints, triggers (step
  062 blocks editing saved results) and JSON columns; SQLite's enforcement is weaker.

## 2.4 Why Git with an SSH key

SSH keys prove identity without typing a password each time. The private key never leaves
the machine.

**Known trap:** Git for Windows and git inside Ubuntu are *separate installations* with
separate configuration. The Windows one still shows the identity "Your Name", and it has no
SSH key, which is why `git pull` from Windows fails with "Permission denied (publickey)".
**All git work is done from Ubuntu.**

## 2.5 The recurring Docker problem (worth knowing)

After an unclean Windows shutdown, Docker Desktop leaves socket files in
`%LOCALAPPDATA%\Docker\run` (names seen: `dockerInference`, `sailor-ingest.sock`,
`userAnalyticsOtlpHttp.sock`). Windows cannot delete them, and the next start fails with
*"The file cannot be accessed by the system"*.

**Fix:** quit Docker Desktop, delete those files from Ubuntu
(`rm -f /mnt/c/Users/bit/AppData/Local/Docker/run/*`), start Docker again.
**Prevention:** quit Docker from the system tray before shutting down or sleeping.
Docker Desktop 4.90 is a per-user install at
`C:\Users\bit\AppData\Local\Programs\DockerDesktop\Docker Desktop.exe`; the Start-menu
shortcut is stale.

## 3.2 What `.gitignore` blocks, and why

- `/data/` — the whole data folder. Rationale: git stores **every version of every file
  forever**, so committing 285 MB once makes every future clone slow, permanently. The data
  is free to download again, and its integrity is provable by checksum.
- `.env`, `.env.*` (but **not** `.env.example`), `*.pem`, `*.key` — secrets.
- `.venv/`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `.hypothesis/`
  — caches that are regenerated automatically.
- `build/`, `dist/`, `reports_out/`, `checkpoints/`, `*.pt`, `*.ckpt` — outputs.
- `~$*`, `.DS_Store`, `Thumbs.db`, `desktop.ini` — operating-system and Office leftovers.
- **Exception:** `!research/tests/fixtures/**` — tiny example files *are* committed so tests
  can run on GitHub without the real dataset.

**Important subtlety (a bug we hit):** the original rule was `data/` without a leading
slash, which in git matches a folder named `data` **anywhere**, including the new source
folder `research/helios/data/`. That silently hid real source code from git. The rule is now
`/data/`, anchored to the project root. Checked with `git check-ignore -v <path>`.

## 4.1 `pyproject.toml` — the single place for project settings

- **Runtime dependencies:** alembic, duckdb, numpy, pandas, psycopg (PostgreSQL driver),
  pyarrow (Parquet), pydantic, pydantic-settings, pyyaml, scikit-learn, sqlalchemy.
- **Development dependencies:** hypothesis, mypy, pandas-stubs, pre-commit, pytest, ruff,
  types-pyyaml.
- **Package location:** `packages = ["research/helios"]`.
- **pytest settings:** `testpaths = ["research/tests"]`,
  `addopts = "--tb=short -m 'not slow'"`, plus a registered `slow` marker.
- **ruff settings:** line length 100, target Python 3.12, rule sets `E, W, F, I, B, UP`,
  first-party package `helios`, and `extend-exclude = ["*.md"]`.
- **mypy settings:** `strict = true`, `plugins = ["pydantic.mypy"]`, plus one narrow
  exception: `sklearn.*` has `ignore_missing_imports = true` because scikit-learn ships no
  type information.

### Why these specific ruff rule sets
- `E`, `W` — style (spacing, line length).
- `F` — real mistakes: unused variables, undefined names, unused imports.
- `I` — import order, so imports never cause noisy diffs.
- `B` (bugbear) — likely bugs, e.g. a mutable default argument.
- `UP` — modern syntax, e.g. `str | None` instead of `Optional[str]`.

**Why `extend-exclude = ["*.md"]`:** ruff 0.16 tried to reformat the Python examples inside
Markdown documents, which would have rewritten documentation text.

### Why mypy in strict mode
Strict mode requires every function to declare what it takes and returns. It catches a whole
class of errors *without running the code* — for instance passing a `str` where an `int` is
expected, or forgetting that a function can return `None`.

## 4.6 `helios/common/config.py` — settings that fail loudly

- `HeliosConfig` is the base for every settings model, with `extra="forbid"` (an unknown key
  is an error, so a typo cannot be silently ignored) and `frozen=True` (settings cannot be
  changed after loading, so a run cannot alter its own configuration halfway).
- `load_config(path, model)` — checks the file exists, parses it with `yaml.safe_load`
  (never `yaml.load`, which can execute arbitrary code), requires a mapping, validates it
  against the model, and wraps every failure in one clear `ConfigError`.
- `canonical_json(config)` — turns settings into text in a fixed way: keys sorted, no extra
  spaces, `NaN` not allowed. This means the same settings always produce identical text.
- `config_hash(config)` — SHA-256 of that text, giving a 64-character fingerprint.

**Why a fingerprint:** two runs with the same fingerprint used exactly the same settings.
Instead of arguing about what was configured, you compare two strings.

## 4.7 `helios/common/lineage.py` — proving where a result came from

`RunContext` is a frozen record with:

| Field | Meaning |
|---|---|
| `code_commit` | the 40-character git commit the code was at |
| `dirty` | whether the working folder had uncommitted edits |
| `config_hash` | the settings fingerprint |
| `data_snapshot_id` | which data was used |
| `seed` | the random seed |
| `created_at` | when the run happened (UTC) |

`RunContext.capture(config, data_snapshot_id, seed, reported=False)` validates the seed and
snapshot id and, when `reported=True`, **refuses to proceed if the working folder is dirty**.

**Why refuse:** if the code is not saved in history, nobody can reproduce that result later.
A result that cannot be reproduced must not be reported.

## 4.8 `helios/common/seed.py` — reproducible randomness

`set_seed(seed)` seeds Python's `random` and NumPy's global generator and returns a fresh
`numpy.random.Generator`. `MAX_SEED = 2**32 - 1`.

**Why:** machine-learning results change with randomness. Fixing the seed makes a result
repeatable; recording the seed in the lineage makes it *provably* repeatable.

# Part 5 — Steps 030–035: the five recorded decisions (ADRs)

## 5.1 What an ADR is and why the project uses them

An **Architecture Decision Record** is a short document with a fixed shape: context, the
decision, the alternatives considered (with pros and cons), the consequences, and how we
would know the decision was wrong. Each has a status (Proposed → Accepted) and a date.

**Why:** decisions made in conversation are forgotten and quietly re-litigated. Worse, a
decision made *after* seeing results can be chosen to flatter those results. An ADR fixes the
decision with a date, so it is verifiably earlier than the results. Changing an accepted
decision requires writing a new ADR.

Files: `docs/decisions/ADR-000-template.md`, `ADR-001` … `ADR-005`, plus `README.md` which
indexes them. All five are **Accepted**, approved by the team lead.

## 5.2 ADR-001 — technology stack

Confirms: Python 3.12 with uv for the 5th semester; C++20 for the 6th/7th-semester hot path;
Go for 7th-semester services; TLA+ for formal specification; PostgreSQL for the registry;
Parquet + DuckDB for research data.

## 5.3 ADR-002 — how an alpha is scored (the gates and the Fitness formula)

The six gates an alpha must pass:

| Gate | Requirement | Purpose |
|---|---|---|
| **G1** | Sharpe > 1 (net of costs) | the idea must earn enough per unit of risk |
| **G2** | Fitness > 1 | it must earn without excessive trading |
| **G3** | 1 % < turnover < 70 % per period | not a do-nothing idea, not a churn machine |
| **G4** | metrics computed out-of-sample | never scored on the data it was built on |
| **G5** | more than 50 % of months have Sharpe > 0 | not one lucky window |
| **G6** | Sharpe > 0 at 2× assumed costs | the edge must survive worse costs |

The Fitness formula:

```
Fitness = Sharpe × sqrt( |annual_return| / max(turnover, 0.125) )
```

- `Sharpe` — annualised, net of costs, risk-free rate 0, using the horizon family's
  periods-per-year.
- `annual_return` — mean net profit per period × periods per year, as a fraction.
- `turnover` — mean of |position(t) − position(t−1)| per period, as a fraction.
- `floor = 0.125` — the smallest turnover the formula will divide by.
- The absolute value is inside the square root only, so **a losing alpha always has negative
  Fitness** (the sign comes from Sharpe).

**Why the floor exists:** without it, an alpha that trades extremely rarely would divide by a
tiny number and get an enormous Fitness score for free. The floor caps that gaming.

**Worked examples from the ADR:** 0.949, 1.386, 1.470, 2.324, and −0.566 for a losing alpha.

**Why G4–G6 were added** (they are not in the original brief): G4 stops an idea being
promoted on in-sample results (an alpha with Sharpe 4 in-sample and −0.2 out-of-sample would
otherwise pass); G5 stops one lucky period carrying the whole result; G6 stops promoting an
edge smaller than realistic costs. Any of them can be disabled by configuration, but
disabling is an audited action.

## 5.4 ADR-003 — horizon families

| Family | Periods per year | Meaning |
|---|---|---|
| `H-HOURLY` | 8,760 | 365 × 24 |
| `H-MINUTE` | 525,600 | 365 × 24 × 60 |
| `H-SECOND` | 31,536,000 | |
| `H-MICRO` | 315,360,000 | |

A 365-day UTC year is used (not 252 trading days) because crypto trades every day. For
comparing across families, Sharpe is also reported on daily-aggregated returns.

**Why this matters:** Sharpe depends on how often you measure. Without a fixed
periods-per-year per family, an hourly strategy and a minute strategy cannot be compared
honestly.

## 5.5 ADR-004 — the exact split dates

All dates are **UTC calendar days, inclusive**.

**H-HOURLY (7-day embargo):**

| Split | From | To | Days |
|---|---|---|---|
| TRAIN | 2018-01-01 | 2022-12-31 | 1,826 |
| *embargo* | 2023-01-01 | 2023-01-07 | 7 |
| VALID | 2023-01-08 | 2024-06-30 | 540 |
| *embargo* | 2024-07-01 | 2024-07-07 | 7 |
| TEST | 2024-07-08 | 2026-08-31 | 785 |

**H-MINUTE (1-day embargo):**

| Split | From | To | Days |
|---|---|---|---|
| TRAIN | 2024-09-01 | 2025-08-31 | 365 |
| *embargo* | 2025-09-01 | 2025-09-01 | 1 |
| VALID | 2025-09-02 | 2026-02-28 | 180 |
| *embargo* | 2026-03-01 | 2026-03-01 | 1 |
| TEST | 2026-03-02 | 2026-08-31 | 183 |

Rules attached to the decision:

1. The embargo must be at least as long as the longest label horizon an alpha uses.
2. Features may look **backwards** across a boundary (that is information available at the
   time); a label whose forward window crosses a boundary is dropped.
3. Warm-up bars at the start of a split are reported as UNAVAILABLE, never as zero.
4. Coins listed later (e.g. SOL in 2020) take part only from their listing date.
5. Data before 2018-01-01 is not used for metrics (thin early months), only as warm-up.
6. TEST may be used **at most twice per alpha**, and every access is logged.
7. Changing a date requires a new ADR; older results keep their old dates.

**Why an embargo at all:** suppose an alpha predicts the return over the next 7 days, and the
last training day is 31 December. Its label depends on prices up to 7 January. Without a gap,
those same days are inside VALID, so training has effectively seen validation data.

**Why chronological, not random:** with random splitting, tomorrow ends up in the training
set and yesterday in the test set. The model then "predicts" a past it has already seen — the
classic way a backtest lies.

## 5.6 ADR-005 — fees and slippage

Binance's published spot fees, checked on 2026-09-20 at
<https://www.binance.com/en/fee/schedule>: regular user 0.100 % maker / 0.100 % taker, or
0.075 % when paying fees with BNB.

**Decision:**

| Item | Value |
|---|---|
| Maker fee | 10 bps |
| Taker fee | 10 bps |
| Slippage per side, BTCUSDT and ETHUSDT | 2 bps |
| Slippage per side, SOLUSDT, BNBUSDT, XRPUSDT | 5 bps |
| Simulator cost per side, BTC/ETH | 12 bps (10 + 2) |
| Simulator cost per side, others | 15 bps (10 + 5) |

Cost per period: `cost_t = turnover_t × cost_bps / 10,000`.
Worked example: an hourly BTC alpha with turnover 0.30 pays
0.30 × 12 / 10,000 = 0.00036 (0.036 %) of capital every hour.

Limit orders in the paper venue pay the maker fee and no slippage, but only fill if the next
bar trades **through** the limit price.

**Why not the BNB discount:** the project holds no BNB and a new account starts at the basic
tier. The conservative assumption is chosen, and the cheaper case is still visible through
the cost-sensitivity sweep (0.5×, 1×, 2×, 3×, 4×).

**Honesty note recorded in the ADR:** the slippage numbers are an **assumption**, not a
measurement. Step 170 compares them with real paper-trading fills; the 6th semester will
measure them from order-book data.

# Part 7 — The FI-2010 machine-learning track

Steps 037, 038 (loading and splitting the data) and 049, 050 (day split and first baseline).

## 7.1 What FI-2010 is

A public benchmark dataset of limit-order-book data: 10 days of trading for 5 Nasdaq Nordic
stocks, published by Ntakaris et al. (2018). HELIOS uses the "DeepLOB" packaging: one zip
containing 4 text files, normalised and with auction periods removed.

| File | Days | Events |
|---|---|---|
| `Train_Dst_NoAuction_DecPre_CF_7.txt` | 1–7 | 254,750 |
| `Test_Dst_NoAuction_DecPre_CF_7.txt` | 8 | 55,478 |
| `Test_Dst_NoAuction_DecPre_CF_8.txt` | 9 | 52,172 |
| `Test_Dst_NoAuction_DecPre_CF_9.txt` | 10 | 31,937 |

Each file is a matrix of **149 rows × one column per event**:

| Rows | Contents |
|---|---|
| 0–39 | the order book: 10 levels × (ask price, ask volume, bid price, bid volume) |
| 40–143 | 104 hand-made features from the paper |
| 144–148 | 5 labels: price direction 10, 20, 30, 50 and 100 events ahead |

Label values: **1 = up, 2 = stationary (flat), 3 = down**.

## 7.2 The loader (`research/helios/ml/fi2010.py`)

- Reads **straight from the zip** so the ~940 MB of text is never unpacked into the
  OneDrive-synced folder.
- Refuses a file that does not have exactly 149 rows, has no events, or contains NaN/infinite
  values.
- `split_matrix()` returns an `FI2010Data` with **one row per event** (the layout ML
  libraries expect): `lob` (events × 40), `features` (events × 104), `labels` (events × 5,
  stored as small integers). `labels_for(k)` picks one horizon.
- Measured load times: train file 16.9 s (304 MB in memory), test files 1.7–3.4 s.

## 7.3 The day split (step 049)

`load_split()` returns three parts, as plain NumPy (no PyTorch anywhere yet):

| Part | Source | Events |
|---|---|---|
| train | first 80 % of the days 1–7 file | 203,800 |
| val | last 20 % of the same file | 50,950 |
| test | days 8, 9, 10 joined | 139,587 |

The validation part is the **last** slice in time order and is **never shuffled**. Shuffling
before splitting would let the model train on events that occur after its validation events —
seeing its own future.

Because the real test loads a 607 MB file (~17 s), it is marked `slow` and excluded from the
default test run; run it with `uv run pytest -m slow`.

## 7.4 Label distribution (measured)

Percentages of up / flat / down:

| File | k = 10 | k = 50 | k = 100 |
|---|---|---|---|
| Train (days 1–7) | 19.7 / **60.5** / 19.7 | 34.4 / 31.7 / 33.9 | 40.6 / 19.4 / 40.0 |
| Test day 8 | 14.1 / **73.2** / 12.7 | 26.2 / 51.2 / 22.6 | 33.2 / 38.7 / 28.1 |
| Test day 9 | 15.0 / 70.3 / 14.7 | 26.8 / 47.2 / 26.0 | 33.2 / 34.2 / 32.6 |
| Test day 10 | 17.4 / 66.8 / 15.8 | 31.2 / 40.6 / 28.2 | 38.3 / 27.4 / 34.3 |

At short horizons most labels are "flat". This single fact decides how models must be scored.

## 7.5 Baseline 1: logistic regression (step 050)

- **Input:** the 40 order-book columns only. **Target:** direction 10 events ahead.
- **Pipeline:** standardise the columns, then multinomial logistic regression
  (`max_iter=200`, `C=1.0`), scikit-learn 1.9.1.
- **Seeds:** 0, 1, 2.
- **Output:** `reports_out/fi2010_logreg_k10.csv`, one row per seed, each carrying the git
  commit, dirty flag, config fingerprint and timestamp.

**Measured result (203,800 train / 139,587 test):**

| Measure | Value |
|---|---|
| Accuracy | 0.7069 |
| Macro-F1 | **0.2814** |
| Always predict "flat" | 0.7066 |
| Fit time per seed | ~9.2 s |
| Difference between seeds | none (identical) |

**Interpretation, stated honestly:** logistic regression on raw order-book levels learns
essentially **nothing** — 70.69 % accuracy against 70.66 % for a model that always answers
"flat". Reported as accuracy alone, "70.7 %" would look like success.

**Why macro-F1 is the gate:** macro-F1 computes the F1 score for each of the three classes
and averages them equally. A model that never predicts "up" or "down" scores ~0 on those two
classes, so its average collapses. Every later model must beat **macro-F1 0.281**.

**Why identical seeds are the expected result:** this solver is deterministic, so equal
numbers across seeds prove there is **no hidden randomness** in the pipeline. The seeds are a
correctness check, not a measure of model variance.

```
https://data.binance.vision/data/spot/monthly/klines/BTCUSDT/1h/BTCUSDT-1h-2026-08.zip.CHECKSUM
```

Saved as `data/binance/spot/klines_1h/BTCUSDT-1h-2026-08.zip`, with the checksum stored

## 8.2 The three layers (built and tested one at a time)

**Layer 1 — plan (step 039).** `Month`, `month_range`, `KlineFile` (which knows its file
name, URL, checksum URL and target path) and `plan_klines`. The command-line tool has a
`--dry-run` mode that prints every file with `exists` or `missing` and a summary. `--symbol
universe` expands to the five coins from `configs/universe.yaml`.

**Layer 2 — download (step 040).**

| Behaviour | Detail | Why |
|---|---|---|
| Streamed in 1 MB pieces | into `<name>.part`, renamed only when complete | a dropped connection cannot leave a half file that looks finished |
| Existing files skipped | checked before any request | re-running is safe and cheap |
| HTTP 404 | reported as `not-found`, **not** retried | that month simply does not exist (before listing) |
| Network errors, 5xx, 429 | retried with waits 2, 4, 8, 16 s | suits a slow or flaky connection |
| Other 4xx (e.g. 403) | not retried | trying again cannot help |
| Exit code | 1 if any file finally failed | so scripts and CI notice |

**Layer 3 — verify (step 041).** Binance's `.CHECKSUM` file has the form
`<64 hex characters>  <file name>`. The tool downloads it, validates its shape, keeps a copy
next to the zip (so later checks need no internet), and compares the file's SHA-256. A
mismatch deletes the file and counts as a failed attempt, so it is downloaded again. Files
already on disk are verified too: good ones are skipped, damaged ones replaced.

Proved by deliberately corrupting a file: it was detected and replaced.

# Part 9 — Steps 045–048: reading, time units, validation, gaps

All of this lives in `research/helios/data/klines.py`.

## 9.1 Reading (step 045)

Each zip holds one CSV with **no header row** and **12 comma-separated columns**:

```
open_time, open, high, low, close, volume, close_time, quote_volume,
trades, taker_buy_base, taker_buy_quote, ignore
```

`read_klines(zip_path)` reads it directly from the zip into a table with those names and
numeric types (`open_time`, `close_time`, `trades` as 64-bit integers; the rest as floating
point). It raises `KlineFormatError` for: a missing file, a file that is not a valid zip, a
zip that does not contain exactly one CSV, an empty file, the wrong number of columns, or a
header row.

**Verified across all 617 files:** every file has 12 fields and no header row.

**Why a separate module from the downloader:** downloading and parsing are different jobs;
`binance.py` was already ~340 lines.

## 9.2 The two time units (step 046) — the single most dangerous detail so far

| Files | Unit | Example |
|---|---|---|
| up to 2024-12 (417 files) | milliseconds | `1733011200000` |
| from 2025-01 (200 files) | microseconds | `1735689600000000` |

`normalise_ts(column)` judges **each value on its own**: at or above `1e14` it is already
microseconds; below that it is milliseconds and is multiplied by 1,000. The result is always
whole-number **UTC microseconds**.

**Why that cut-off is safe:** as microseconds, `1e14` is March 1973; as milliseconds it would
be the year 5138. Real market data cannot fall on the wrong side.

It refuses: a non-integer column, an empty column, or any value that lands outside 2009–2100
after conversion (so a file written in *seconds* fails loudly instead of silently becoming
1970).

`normalise_klines(frame)` converts `open_time` and `close_time` on a **copy**.
`to_utc(micros)` converts to readable timestamps for humans; the stored value stays an
integer because integers are exact, small, sort correctly and have no time-zone ambiguity.

**Proof on real data:** four real months spanning the change (2024-11 → 2025-02, 2,880
candles) join into one strictly increasing timeline whose only gap between neighbours is
exactly 3,600,000,000 µs.

**Precision detail worth knowing:** in millisecond files a candle's `close_time` ends 1
**millisecond** before the next candle starts; in microsecond files 1 **microsecond**. A test
initially assumed 1 µs everywhere and failed — the code was right, the test was wrong.

## 9.3 Validating rows (step 047)

`validate_bars(frame)` returns **only the offending rows**, unchanged, with a `problems`
column naming every rule each row breaks (several can break at once). It never repairs or
drops anything.

Rules: missing value; a price at or below zero; high below open or close; low above open or
close; high below low; negative volume or quote volume; negative trade count; taker-buy
volume above total volume.

**Result on the real data: 0 bad rows out of 5,617,391 candles.** That is the baseline: from
now on, any non-zero count means something really changed.

## 9.4 Gaps, duplicates and off-grid candles (step 048)

- `find_gaps(frame, interval)` builds the expected timeline and returns **one row per
  unbroken run** of missing candles, with start, end, count and readable UTC times.
- `find_duplicates(frame)` returns every copy of a repeated timestamp.
- `find_off_grid(frame, interval)` returns candles whose timestamp is not an exact multiple
  of the interval.
- `find_gaps` **refuses** to run on off-grid data rather than guessing.

**Nothing is ever filled in.** A missing hour means the exchange was down. Filling it with
the previous price would put an invented number into every feature, every backtest and every
result built on it, and a strategy could look profitable because of data we made up.

**Measured on the full history:**

| Coin | Hourly candles | Gap runs | Missing | Duplicates | Off-grid |
|---|---|---|---|---|---|
| BTCUSDT | 79,117 | 28 | 170 | 0 | 43 |
| ETHUSDT | 79,117 | 28 | 170 | 0 | 43 |
| BNBUSDT | 77,181 | 27 | 163 | 0 | 43 |
| XRPUSDT | 72,913 | 25 | 87 | 0 | 0 |
| SOLUSDT | 53,063 | 10 | 19 | 0 | 0 |
| every coin, minute | 1,051,200 | 0 | 0 | 0 | 0 |

Largest outages: **75 hours, 2018-02-08 01:00 → 2018-02-11 03:00** (BTC, ETH, BNB);
10 hours on 2018-06-26; 10 hours on 2019-05-15; 8 hours on 2019-08-15.

**The February 2018 oddity:** in the same month, 43 candles for BTC, ETH and BNB restart
**off the hour**, e.g. `2018-02-09 09:28:14.789` instead of `09:00` (640 candles that month
instead of 672). The files are not damaged — their checksums match Binance's. This is how the
exchange recorded the restart after its outage. The candles are kept and reported; a program
that assumed a fixed one-hour spacing would silently shift every timestamp by 28 minutes.

# Part 10 — Steps 051–053: the Parquet store and the reports

## 10.1 `build_bars.py` — the pipeline

For one coin and interval: read every monthly zip → put timestamps in one unit → validate →
find off-grid rows → drop duplicate timestamps → sort → write **one Parquet file per calendar
year**.

Output layout (Hive style, so DuckDB and pyarrow read the folder names as columns):

```
data/processed/bars/source=binance/interval=1h/symbol=BTCUSDT/year=2019/bars.parquet
```

The `ignore` column is dropped (it is always 0 and means nothing). Compression is `zstd`.
Off-grid bars **are** written, because they are real trades; they are recorded in the report.

`BuildResult` carries: rows written, files written, months read, duplicates dropped, the bad
rows, the gaps and the off-grid rows.

**Measured build:** 61 Parquet files, **285 MB**, **5,617,391 bars**, 0 bad rows, 0
duplicates; hourly build 14 s, minute build 28 s.

## 10.2 Why Parquet

| Option | Verdict |
|---|---|
| Keep the zips | Must unzip and parse text every time — about 25 s for a year of minute data |
| CSV | Still text; slow to parse, and column types are lost |
| **Parquet (chosen)** | Binary, compressed, typed, column-oriented. A year of minute bars (525,600 rows) reads back in **0.44 s** |

## 10.3 The reports (step 052)

Written beside the bars:

```
data/processed/reports/validation_BTCUSDT_1h.parquet
data/processed/reports/gaps_BTCUSDT_1h.parquet
```

- **Validation report columns:** symbol, interval, open_time, open_time_utc, problems.
  Off-grid rows appear here with the problem `timestamp not on the interval grid`.
- **Gap report columns:** symbol, interval, gap_start, gap_end, missing, gap_start_utc,
  gap_end_utc.

**Reports are written even when clean.** A report that exists and says "nothing wrong" is
evidence; a missing file only means nobody looked.

Real result: 20 report files. BTC/ETH/BNB hourly each list 43 off-grid candles; all minute
reports are empty.

## 10.4 `docs/research/data_quality.md` (step 053)

Generated by `scripts/data_quality_report.py`, which reads the Parquet reports. **No number
is typed by hand.** It records the commit it was generated from and whether the working

It also states the consequences for research:

1. The hourly history is usable — the worst coin is missing ~0.2 % of its bars.
2. A gap means "unknown", never "no change".
3. The February 2018 off-grid bars sit inside the hourly TRAIN period, so features must read
   **timestamps**, not row positions.
4. The minute data needs no special handling.

`resample_bars` builds longer bars from shorter ones:

| Output value | Rule |
|---|---|

# Part 12 — Steps 056–057: PostgreSQL, Alembic and the first tables

| code_commit, config_hash, notes | optional |
| snapshot_id | foreign key to `data_snapshots`, `ON DELETE RESTRICT` |

**Why `ON DELETE RESTRICT`:** the data behind a result must not be able to vanish underneath
it. Deleting a snapshot that an experiment references is refused by the database.

**Why `NUMERIC` and not floating point:** with floats, `0.1 + 0.2 = 0.30000000000000004`.
Prices and sizes must never drift.

**Why rules in the database and not only in Python:** a Python check protects only code that
remembers to call it. A database constraint holds for **every** insert — from any script, any
teammate, or someone typing SQL into Adminer.

Verified: `upgrade head` → 3 tables; `downgrade base` → clean; `upgrade head` again → 3
tables. The migration works in both directions.

16 tests run against the real PostgreSQL inside a transaction that is **rolled back**, so
they leave nothing behind, and they skip when no database is reachable (e.g. CI).

# Part 16 — Every bug found, and what it teaches

| # | Bug | How it was found | What would have happened | Lesson |
|---|---|---|---|---|
| 1 | An end date written as text (`"2023-06-30"`) was treated as midnight | a test, confirmed by real counts: June gave 697 hours instead of 720; a minute year gave 524,161 instead of 525,600 | the last day of **every** test window silently missing | boundary handling needs tests with known counts |
| 2 | `numpy.int64` is not a Python `int`, so a timestamp taken from a data column crashed the loader | the cross-check script | the most natural way to call the function failed | test with the values real code actually passes |
| 3 | A failing test printed the database password inside its traceback | reviewing test output | a real secret exposed in logs and CI | `--tb=short`; verified by counting (never printing) occurrences: 0 |
| 4 | `.gitignore` rule `data/` also hid the new source folder `research/helios/data/` | `git check-ignore -v` before committing | new code never reaching GitHub; CI failing on a missing module | anchor ignore rules with a leading slash |
| 5 | `docker compose -f infra/…` from the project root could not find the settings | running it | every teammate rediscovering the same error | document the exact working command |
| 6 | A test wrongly assumed every candle ends 1 µs before the next | the test failed | nothing — the code was right | when a test fails, first ask whether the test is wrong |
| 7 | ruff tried to reformat Python examples inside Markdown documents | a check run | documentation text silently rewritten | exclude documents from code formatting |
| 8 | `astral-sh/setup-uv@v10` did not exist | CI failing | broken CI | pin exact versions of external actions |

# Part 17 — The project's standing rules

1. **Never fill in missing data.** Report it.
2. **Never repair a bad row.** Report it.
3. **Never type a result by hand.** Generate it, with lineage.
4. **Never report a result from a dirty working folder.**
5. **Never commit data, passwords or generated outputs.**
6. **Never change an accepted decision** without a new ADR.
7. **Never use the TEST period more than twice per alpha**, and log every use.
8. **Never judge a classifier on accuracy alone** when one class dominates.
9. **Never split time-series data randomly.**
10. **Prices and sizes are exact decimals**, never floating point, in the database.
11. **Timestamps are whole-number UTC microseconds** everywhere.
12. **Every rule that can be enforced by the database should be.**
